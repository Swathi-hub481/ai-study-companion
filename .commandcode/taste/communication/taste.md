# Communication

- Expects a structured end-of-task report: root cause, exact fix, observed metrics/values, test results, and an explicit statement of whether the manual acceptance test now passes. Confidence: 0.85
- Expects proactive disclosure of any side effects or damage caused during the work (e.g. rows left in a broken state), even when already repaired. Confidence: 0.8
- For multi-pass UI work, expects a fixed stop-and-report checklist after every pass before proceeding: files changed, components changed, backend files changed Y/N, API files changed Y/N, database/schema files changed Y/N, new dependencies Y/N, additional network requests Y/N, additional database queries Y/N, typecheck/lint/build PASS-FAIL, performance impact, pages redesigned (with a short per-area summary of what changed), the differences from the reference image that remain, and visual changes completed — plus an explicit confirmation that the next pass was NOT started — followed by waiting for the next instruction. Confidence: 0.8
- For a large phase, expects a comprehensive numbered final report: what components/screens changed, design system changes, responsive/accessibility/performance improvements, dependencies added or removed, explicit confirmation that untouched functionality was preserved, verification results, remaining issues, and a short list of screens worth reviewing manually. Also expects deliberate omissions to be stated with the reason rather than left silent. For a performance phase, the report must carry a measured before/after table, only the causes that were actually verified, the optimizations tried and then reverted with the reason, and the remaining bottlenecks named honestly instead of worked around. Confidence: 0.7
