# Workflow

- Requires a full verification battery after changes — typecheck, lint, the entire test suite, the evaluation suite (`npm run eval`) and diagnostic loop (`npm run diag:loop`) where the project has them, and a production build — before work is called done; running only the touched tests is not enough. Confidence: 0.9
- Enforces strict phase discipline: do not advance to the next phase until the current phase passes manual verification/acceptance, and for multi-part work (e.g. a page-by-page redesign) wants it implemented strictly one pass at a time — stop and report after each pass, then wait for the next instruction instead of continuing autonomously. Confidence: 0.85
- Insists existing state (database, uploaded materials, user projects) be preserved — do not delete or recreate it unnecessarily. Confidence: 0.8
- For investigation/diagnostic requests, expects read-only behaviour: inspect and report what actually exists (files, schema, DB rows, available commands) without modifying code or data, and end with the safest recommended next step for them to act on. Explicitly gates any mutation behind their approval ("say the word"). Confidence: 0.7
- Prefers tests to run against the mock AI provider where possible rather than live providers. Confidence: 0.7
- Gives explicitly ordered investigation checklists and expects each enumerated step to be addressed, not summarized away. Confidence: 0.7
- Expects the actual reference artifact to be re-inspected directly before any code changes — for an image, read with vision and cropped into per-panel regions at readable resolution, each read individually, rather than trusting a previous textual description or treating it as general inspiration — and expects the current implementation to be inspected and compared against that reference as an explicit step (inspect reference → inspect implementation → compare → then implement). This sequence is demanded again even when a design system was already built from the same reference in an earlier pass. Confidence: 0.8
- After implementing, expects the running app to be exercised manually on the affected routes, not just statically checked: start the app, sign in as a real account (find a user/project that genuinely holds data so the test is meaningful), load each affected route, and confirm the expected elements render, navigation and existing buttons/links work, real existing data appears, and no backend behaviour changed. Confidence: 0.75
- When blocked by an external/paid-dependency failure (e.g. billing/quota exhaustion), expects a stop-and-report of the exact verbatim error rather than workarounds, faked results, or premature asks to buy/resolve it. Confidence: 0.7
- Prefers no-cost model tooling over paid vendor APIs: moved generation to Groq (`openai/gpt-oss-120b`) and accepted local/in-process embedding models rather than paying for OpenAI credits. Confidence: 0.5
- Expects awareness that their shell exports stale environment variables that shadow `.env`/`.env.test` (`AI_*`, `NODE_ENV=production`, `DATABASE_URL`); these must be verified or cleared (and `NODE_ENV` unset before `npm install`) rather than assuming dotenv values apply. Confidence: 0.6
- For a substantial feature or phase, wants a written plan reviewed and approved before implementation begins, covering the goal, an explicit scope boundary, the key decisions, files to add/modify, the test plan, verification steps, and risks. Confidence: 0.65
- Scopes each phase strictly: work the specification assigns to a later phase is deliberately excluded and deferred (e.g. weakness detection, growth bands, recommendations left to Phase 8) rather than pulled forward, with the boundary stated explicitly. When offered scope options for the current phase, also defers the heavier optional part of an in-scope requirement to a later phase (e.g. committed evaluation baselines and diffing, though the spec asks for them), choosing the immediately deliverable subset. Confidence: 0.75
- Prefers to be handed deploy/release artifacts plus a runbook (Dockerfile, compose services for web and worker, migration and post-deploy checklists) and to run anything needing their own accounts, credentials, or paid infrastructure themselves — does not want the agent provisioning hosting or performing a real public deployment on their behalf. Confidence: 0.6
- Wants limitations documented honestly and kept current (a `docs/limitations.md`-style file): what is unimplemented, untested, or simplified, stated plainly with the upgrade path — and the README's claims kept matching what the repository actually contains (e.g. a non-existent Playwright suite was removed rather than left advertised). Confidence: 0.7
- Treats a performance/optimization phase as strictly behaviour-preserving: routes, API contracts, database semantics, retrieval/evidence/citation behaviour, grading, mastery, analytics, auth and project isolation must all stay functionally identical, with speedups coming only from eliminating unnecessary work, parallelizing independent work, or caching safe deterministic computation. Confidence: 0.75
- Gates changes to AI provider/model configuration behind explicit approval plus profiling evidence — do not silently swap the generation model for a faster one, and if measured provider latency is the ceiling, say so rather than optimizing around it. Confidence: 0.7
- When a test fails after a change, expects the cause to be established before moving on — isolate it experimentally (e.g. revert the suspect change and re-run just the affected files) instead of assuming it is environmental, and flag any pre-existing failure as pre-existing rather than absorbing it — and, when the current task is unrelated to it, leave that failure in place rather than "fixing" it as a side effect. Confidence: 0.75
- When a production build follows a session of running the dev server, expects stale build artefacts handled at the artefact level — clear `.next` (`Remove-Item -Recurse -Force .next`) and rebuild cleanly — and never by editing application code to work around the stale-`.next` error; such failures should be reported as an artefact/environment issue rather than a code defect. Confidence: 0.7
- Distrusts filtered or truncated command output: when a reading looks inconsistent with expectations (e.g. a filtered build summary showing "0 B" shared JS against a previously observed 103 kB), re-runs the command unfiltered to confirm and reports the corrected number rather than trusting the slice. Confidence: 0.6
- Keeps the working tree clean of temporary scratch artifacts created for the task — throwaway helper scripts (e.g. an image-crop script under `scripts/`) are created to do the job and deleted before the work is reported as done — and equally leaves no dev servers or stray listeners behind on the ports used for verification, confirming the ports are free before reporting. Confidence: 0.55
- For a "final consistency" pass, expects an explicit audit across every page before editing (grep each candidate axis rather than guessing) and unification to one convention per axis — page-heading label, section-nav position relative to the title, subtitle colour token, table row rules, page-root spacing rhythm — with the counts reported; changes that are semantic rather than cosmetic (e.g. removing breadcrumbs / altering navigation) or refactors with zero visual payoff (e.g. consolidating 13 hand-rolled headings into one component) must be surfaced as decisions for the user rather than made unilaterally. Confidence: 0.6
- On Windows/PowerShell, file paths containing Next.js route groups and dynamic segments (`app/(app)/...`, `[userId]`) break glob expansion and PowerShell array/argument parsing — wants explicit, individually quoted file paths passed to CLIs like prettier, and grep (which handles them) used to read those files instead of glob-based file readers. Confidence: 0.55
- For a reported bug or runtime/rendering error, wants the failure reproduced first and the exact root cause identified before any code is touched, then only that cause fixed — no speculative or unrelated changes, no redesign, no "while I'm here" improvements layered onto a bug fix, and no begin-the-next-task behaviour until the failure is resolved and reported. Confidence: 0.7
- When a runtime failure is known/confirmed to be environmental rather than a code defect (e.g. "Can't reach database server at localhost:5433", Docker Desktop port-proxy flakiness), wants it resolved at the environment level — verify/restore the service (e.g. restart the database container) and confirm the app then renders — with zero application, Prisma/schema, configuration, backend, API, or performance-code changes made to work around it. Confidence: 0.6
- Wants a failing or runtime-error route verified by actually loading it in a real browser (client-side render/hydration), not just via HTTP/status-code probes or server-side rendering checks — and after a fix, wants the adjacent affected routes (e.g. the larger feature's other pages) and login/session re-verified so the fix did not break them. Confidence: 0.6
- Gates installing new global/system tooling behind explicit approval — when a needed CLI (e.g. a browser-automation tool for visual verification) is not present, does not install it unprompted, reports the gap, and offers to install it on request ("say the word"). Confidence: 0.6
- Runs the project formatter over the files it touched (e.g. `npx prettier --write` on the changed paths) before kicking off typecheck/lint/build. Confidence: 0.5
